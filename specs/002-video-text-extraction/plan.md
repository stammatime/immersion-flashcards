# Implementation Plan: Video Text Extraction for Anki Flashcards

**Branch**: `002-video-text-extraction` | **Date**: 2026-04-19 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/002-video-text-extraction/spec.md`

## Summary

A post-processing pipeline that takes a recorded gameplay video, scans frames for on-screen
text in the user's target learning language (Japanese, Chinese, or English), extracts the
text via OCR, builds a deduplicated flashcard deck with screenshots, and exports an
Anki-compatible package file. The full transcript of all detected text is also saved. Built
in Python 3.11+ using the existing PyQt6 UI, with OCR handled by a suitable engine and
video frame extraction via FFmpeg (already a project dependency).

## Technical Context

**Language/Version**: Python 3.11+
**Primary Dependencies**: PyQt6 (GUI), FFmpeg 5.0+ via subprocess (frame extraction), OCR engine (see research.md), genanki (Anki deck generation), pytest (testing)
**Storage**: JSON file for extraction session metadata; Anki .apkg package files + media folder for output; transcript as structured text file
**Testing**: pytest + mocked OCR responses for unit tests; integration tests with sample video frames
**Target Platform**: Windows 10+, macOS 12 (Monterey)+
**Project Type**: Desktop application (extends existing single-window PyQt6 app)
**Performance Goals**: Process a 30-minute video within a reasonable timeframe; frame sampling to avoid redundant OCR on identical frames
**Constraints**: Offline-capable OCR (no cloud API dependency); must handle CJK text accurately; output must import cleanly into Anki desktop
**Scale/Scope**: Single-user desktop app; one extraction session at a time; videos up to several hours

**Structure Decision**: Extends the existing single-project structure. Two new top-level
modules under `src/` — `extractor/` for video processing and OCR, `anki/` for deck
generation and export. Keeps the existing `recorder/`, `settings/`, and `ui/` modules
intact. The `anki/` module is separated from `extractor/` because deck generation is a
distinct concern that could be reused by future features (e.g., manual card creation).
